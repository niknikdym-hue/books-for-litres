# 1. Главный UX-принцип

Пользователь не должен видеть архитектуру проекта.

Он должен понимать только:

1. какую книгу / материал он выбрал;
2. что именно хочет озвучить;
3. каким движком и голосом;
4. сколько это примерно займёт / сколько будет стоить для облака;
5. что сейчас происходит;
6. где готовый результат;
7. что делать, если задача прервалась.

Не строить интерфейс как набор технических dialog/alert окон.
Не требовать Terminal.
Не показывать пользователю пути к Python, JSON, manifests, fingerprints, request IDs и логи без отдельного режима «Подробности».

---

# 2. Нужен НАТИВНЫЙ macOS UI

Текущий AppleScript launcher считать временным техническим bootstrap/fallback.

Сначала проверить локальный toolchain:

```bash
xcrun swiftc --version
xcodebuild -version
```

Предпочтительная реализация:

```text
Swift + SwiftUI
```

Если полноценная локальная сборка нативного SwiftUI `.app` невозможна из-за отсутствия нужного toolchain — НЕ заменять это очередной цепочкой AppleScript dialog и НЕ ставить пакеты автоматически.

В таком случае STOP и сообщить точную недостающую системную зависимость.

Если toolchain доступен — реализовать native app.

---

# 3. Архитектура GUI

GUI — только frontend/orchestrator.

Не переносить TTS-логику в Swift.
Не дублировать HTTP-клиент Yandex.
Не переписывать Qwen generation.

SwiftUI-приложение должно вызывать существующий Python universal bridge / backend через `Process` и получать структурированный JSON/TSV output.

Существующие Python backends остаются source of truth.

При необходимости расширить `audiobook_studio_app_runner.py` новыми OFFLINE командами для UI, но:

- не ломать существующий CLI contract;
- реальные Yandex requests разрешены только явным run action;
- health/list/estimate/status должны быть offline или явно маркированы;
- errors возвращать структурированно, пригодно для UI.

# 5. Экран / блок «Библиотека»

Слева показывать понятный список подготовленных книг.

Для каждой:

- название;
- автор;
- краткий статус последней генерации, если есть.

Не показывать `.json` filename как главное имя.

Если сейчас book profiles доступны только через существующий Qwen catalog — использовать его как источник.

Кнопка `+ Добавить книгу` может быть disabled/marked «скоро», если полноценный import TXT ещё не реализован. Не делать фиктивную кнопку, которая ничего не объясняет.

# 6. Выбор движка

Движок должен переключаться очевидно:

```text
Qwen — локально
Yandex SpeechKit — облако
```

Лучше segmented control / две большие карточки, а не dropdown с техническими ID.

При выборе показывать только релевантные настройки.

### Qwen

- голос;
- существующие book/job параметры;
- пометка «Локально · без тарификации API».

### Yandex

Для текущего production-профиля:

```text
Lera
neutral
1.04
```

Пока это утверждённый профиль — не перегружать пользователя десятками неиспользуемых настроек.
Можно показать:

```text
Голос: Lera
Стиль: neutral
Скорость: 1.04
```

как аккуратные controls/info.

# 7. Что озвучивать

Интерфейс должен быть готов к четырём scope:

```text
Тестовый фрагмент
Фрагмент
Глава
Вся книга
```

На текущем этапе разрешать только реально поддержанные backend-команды.

Не делать активными варианты, которые ещё не подключены.
Disabled option должен иметь краткое объяснение, например:

```text
«Будет доступно после подключения TTS-master книги»
```

ВАЖНО: текущий незавершённый литературный master книги «Хватит себя обесценивать» автоматически не использовать.

# 8. Оценка ДО запуска

Для Yandex до кнопки Start пользователь должен видеть:

```text
Символов: N
Сегментов: N
Billing units: N
Ориентировочная стоимость: ... ₽
```

Если unit price ещё не подключён — UI не должен притворяться, что цена рассчитана.
Показывать корректно:

```text
Стоимость: тариф не настроен
```

и отдельно подготовить backend contract для цены.

Не хардкодить выдуманную стоимость.

Архитектурно предусмотреть local hard limit стоимости до реального запуска полной книги.

# 9. Start / Resume / Stop

Это ключевой рабочий UX.

### Start

Главная action-кнопка одна и понятная:

```text
Начать озвучку
```

Для Yandex перед первым платным request — один понятный confirmation sheet с итогом:

```text
Yandex SpeechKit
Lera · neutral · 1.04
67 сегментов
Ориентировочная стоимость: XX ₽

[Отмена] [Начать озвучку]
```

Не показывать техническую страшилку про API request на каждом шаге.

### Resume

Если существует незавершённый job:

```text
Продолжить с сегмента 25
```

должно быть первичным пользовательским действием.

Не заставлять пользователя искать job-dir.

### Stop

Нужен безопасный пользовательский вариант:

```text
Остановить после текущего сегмента
```

Не убивать процесс в момент записи WAV/manifest без необходимости.

Если Pause ещё невозможно корректно реализовать без изменения backend orchestration — не делать фальшивую кнопку Pause. Сначала реализовать безопасный Stop/Resume.

# 10. Прогресс

Пользователь после запуска должен видеть реальный статус, а не сообщение «запущено, смотри лог».

Минимум:

```text
24 из 67 сегментов
36%
текущий этап: синтез / сборка
```

Для Yandex желательно дополнительно:

```text
готово из cache: N
новых requests: N
```

но это можно убрать под `Подробности`.

UI не должен зависать во время Python job.
Процесс запускать асинхронно.

Status polling / manifest watching должен быть лёгким и не отправлять сеть.

Пользователь не должен вручную переходить в `renders-yandex/demo/...`.

# 12. Ошибки

Никаких Python tracebacks в основном UI.

Пользовательские сообщения:

```text
Не удалось подключиться к SpeechKit.
Попробуйте повторить позже.
```

или

```text
Audiobook Studio не получила доступ к учётным данным Yandex.
Откройте Настройки → Yandex SpeechKit → Проверить подключение.
```

Для специалиста отдельная раскрываемая секция:

```text
Технические подробности
```

где можно показать category, request id, log path и т. п.

Не показывать credential value.

1. собрать новый native app под временным локальным именем/путём;
2. провести offline UI tests;
3. проверить Qwen catalog/list commands без генерации;
4. проверить Yandex offline estimate/status без сети;
